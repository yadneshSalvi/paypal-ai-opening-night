# Production account and wrap desk

The wrap desk joins attributed baseline and approved entries, reported external cash, original ticket/rental receipts, normalized crew liabilities and exact payout observations. It does not turn the recovery comparison into profit, infer wages from a schedule, or treat an invoice as collection.

## Definitions and immutable sources

All money is integer USD minor units. Baseline estimates, approved obligations, producer-reported external payments, corroborated processor principal, known fees, returned funds and holds remain separate measures. Outstanding cost subtracts corroborated principal and attributed external payment from the approved balance. Reserved transfers are part of outstanding obligations. Credits are balances requiring review, never automatic deductions or refunds. Current net movement is current cash in minus cash out and known fees; missing fees make it incomplete. External cash is shown separately. Historical net principal retains qualified original transactions and subtracts retained identified returns; the original gross receipts remain in the evidence register.

Entries are attributed immutable versions with source references. Signed adjustments retain the approved original; invoice-bound or adjusted entries cannot be rewritten. Cash corrections retain their predecessor. External returns cannot exceed their own reported payments. Invoices and reported external cash cannot collect the same entry twice. Current personal reports, rates, original payable calculations and transfer allocations remain available in the private evidence appendix, including work awaiting review without an inferred liability.

Capture/refund identity, original parent, currency and amount are checked before summing. Identical historical receipt repetitions count once; conflicting amounts or parents hold the account. Pending/adverse original observations withdraw current proof while retaining earlier receipts. Authorization and deposit releases remain exposure rather than expense. Observed acquiring fees must reconcile gross, fees and net for the exact capture/refund. Payout fees come from corroborated item observations; estimated batch fees are not substituted. Supplier acquiring fees are not venue expenses.

The report definition contains the exact tenant, production-lifetime period, venue timezone, as-of time, denominator, integer amounts, unresolved findings and source digests for the production, wrap, settlement and payout revisions. The account grid, accessible table, grouped comparison and cost waterfall consume that definition. Bryntum Grid filters and selection determine the visible comparison cohort. Exports always retain the whole original definition. AG Charts Community 14.3.0 supplies the charts; there is no Bryntum Chart entitlement claim.

## Owned-party invoice authority

The pinned `@fracture/paypal-core` 0.2.4 public methods implement create, original read/search, share-link issuance and cancellation. The installed APIMatic `paypal` 2.29.0 has no invoice controller; no fictional generated endpoint is used. The app guard verifies the complete original envelope around those immutable core methods. The separate [core extension request](architecture/invoice-core-extension-contract.md) remains root-owned.

Set `OPENING_NIGHT_INVOICE_PARTIES_JSON` only to explicitly admitted, owned sandbox parties. Each entry requires `id`, `tenantId`, `label`, `issuerEmail`, `recipientEmail`, `purposePrefix`, `currency: "USD"`, `maxInvoiceMinor`, exact `merchantFingerprint`, `expiresAt` and `controlledSandbox: true`. The server supplies issuer, recipient, item purpose and amount from the admitted party and approved entry. The user cannot supply a caller amount, recipient, URL or authority extension. An empty list disables preparation.

Preparation retains a local original and exact invoice number/reference. Create, issue and cancel each require a separate four-check review and ten-minute grant. Send/cancel also require a fresh original observation, its raw digest and complete normalized envelope: full party digests, amount, one item/quantity, invoice and due dates, payment terms, note/memo and adjustments. Future invoice dates, extra recipients, tips, partial-payment policy or other unsupported drift are held. Both `send_to_recipient` and `send_to_invoicer` are always false. The provider share link is exposed only after verified issuance; controlled fixture links are clearly labelled and never opened as usable provider invoices.

A final preflight persists its evidence and rechecks exact session, role, tenant, admission, approved entry and grant at the actual mutation boundary. Unknown dispatches never create replacements or repeat a send/cancel. A known original uses GET only. Lost creation uses the saved exact number and reference, complete search pagination and one matching original. Changed, missing or reused invoice payment/refund IDs cannot qualify collection. External/marked/pending states and incomplete aggregates are not processor cash. Cancellation or refund does not silently rewrite earned revenue; an attributed adjustment is separate.

## Toolkit and assistant

The actual installed PayPal Agent Toolkit 1.11.0 public OpenAI adapter exposes exactly `get_invoice`, `get_order` and `get_refund`. Its catalog configuration alone is not a dispatch permission: the application intercepts the Toolkit-owned CommonJS axios instance, checks the guard before constructing the Toolkit, and allows only OAuth plus the exact server-owned GET under current authority. Redirects, arbitrary IDs, query strings, additional requests and all mutation tools are denied. Raw responses and hashes are encrypted; the product shows concise receipts with details behind evidence controls.

The finance assistant uses the configured `gpt-6.1-sol` / `max` Responses contract. Each request, provider response identity, tool claim and result is durable. It has a 20-minute original authority, at most eight model steps, one tool per response and bounded input/output. Crew facts are aggregate; raw recipient addresses, payment identities, authority and private source payloads are not sent to the model. It may read the current account, invoke one server-listed Toolkit read, or save an unapproved source-bound proposal. It cannot approve entries, invoices, transfers or messages. Known model identities are polled; unknown dispatch outcomes are retained without replacement POST. Earlier analyses have session-bound cursor pagination.

## Report editions and exports

Sealing first renders a complete definition, then checks source revisions again before committing the edition and exact PDF/JSON bytes. Concurrent source changes reject the seal. PDF output uses `pdf-lib` 1.17.1, `@pdf-lib/fontkit` 1.1.1 and bundled OFL Noto Sans fonts, with repeated table headers, page numbers, wrapped long identifiers, scope and limitations, reconciliation findings, source manifest and full instruction/receipt appendix. Unsupported glyphs appear as explicit Unicode code points; the JSON preserves exact original text. Oversize output fails rather than truncating. Downloads verify original content hashes; a later source, code change or adverse read does not regenerate an old edition. Access remains restricted to the current producer session of that tenant.

The supported bounds are 16,000 retained wrap records, 1,000 report editions, 64 MB PDF, 32 MB JSON and 2,000 PDF pages. Bounds fail explicitly. The account table paginates all rows and the assistant pages all retained runs. Finance HTTP bodies are bounded at 32 KB, model requests at 500 KB and scoped provider reads at 2 MB.

## Local qualification

Use `npm run test:wrap` with a newly restricted local PostgreSQL role/database and the provider-disabled preload. `npm run qa:wrap:export` writes the long export fixture. The frozen 4538 review uses `scripts/qa/wrap-fixture-provider.mjs`, `wrap-review-server.mjs` and an ignored exact private fixture file, never hosted configuration. The review harness uses a distinct `opening-night-wrap-4538-session` cookie and translates it only inside this loopback process. It therefore does not overwrite the owner cookies of protected runtimes. Crew chooser entries use their retained personal fragment capability and leave the producer cookie unchanged. No session or grant expiry is renewed by the chooser.

The initial Toolkit qualification attempt used the wrong axios instance and may have attempted an OAuth request with dummy identifiers. Its egress outcome remains **unknown**; no successful actual provider read/action is claimed. Failed attempts remain in the private qualification ledger. Corrected tests verify credential blanking and fetch/HTTP/HTTPS blocking before Toolkit construction. All qualification here is injected transport, restricted real PostgreSQL and real loopback HTTP. Root owns native browser and any actual provider qualification.

The Toolkit dependency tree still has transitive npm advisories; see [dependency review](architecture/wrap-dependency-review.md). A passing scoped test is not a claim that the whole dependency tree is vulnerability-free.

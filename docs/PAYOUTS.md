# Exact recipients and original payout items

**Wrap & settlement** has a separate transfer desk after reported hours, rates and approved liabilities. The producer reviews an operator-admitted controlled sandbox account for each person, selects available approved balances, and reviews the exact recipient, amount, credits, earlier allocations and additional fees. Four independent checks and a review note precede transfer authority. The personal **Hours** view includes only that person's own payout item history.

This implementation uses the unchanged `@fracture/paypal-core` 0.2.4 `SandboxCommerceRestGateway` typed REST extension. The installed APIMatic `paypal` 2.29.0 SDK has no Payouts controller. Its actual methods are `createPayout`, `getPayoutBatch`, `getPayoutItem` and `cancelUnclaimedPayout`. Primary contracts: [PayPal Payouts API](https://developer.paypal.com/api/payments.payouts-batch/v1) and [authoritative schema](https://developer.paypal.com/api/payments.payouts-batch/v1/schema.json). A batch `SUCCESS` means processing completed; each original item's direct read determines whether its exact recipient was credited.

## Controlled recipient admission

`OPENING_NIGHT_PAYOUT_RECIPIENTS_JSON` is private server configuration, initially `[]`. Every admitted object must contain exactly these fields:

| Field | Meaning |
| --- | --- |
| `id` | Stable operator admission identity, up to 128 safe identifier characters |
| `tenantId`, `personId` | Exact production UUID and existing crew-person identity |
| `label` | Human-readable account description |
| `recipientType` | `EMAIL` or `PAYPAL_ID` |
| `receiver` | Exact controlled sandbox account identifier, with no whitespace |
| `merchantFingerprint` | SHA-256 of the venue's fixed sandbox environment, API host, isolated project and client ID |
| `expiresAt` | Explicit ISO UTC expiry |
| `maxPayoutMinor` | Positive integer USD cents, at most 10,000,000 |
| `controlledSandbox` | Must be `true` |

Only a current producer can read these admissions. A browser cannot submit an email, provider recipient, currency or amount in a transfer command. Recipient approval binds the current admission digest, roster identity and previous version. Changes or expiry require a new review. An account cannot be inferred from a person's name or generated by a model. The admission declaration is an operator assertion; configuration alone does not prove ownership, capability or funding. Actual qualification must use an owned controlled account on the isolated venue merchant. The existing Brightline merchant stays separate.

The current producer read exposes the configured merchant fingerprint even before recipients are admitted. An operator can use that value when preparing the private registry for an already-created production. A changed client ID changes ownership; a rotated client secret replaces the cached gateway without changing the merchant fingerprint. Never put real registry contents, credentials or recipient identifiers in Git, model context, public diagnostics or exports.

## Review, allocation and dispatch

A transfer includes one to twenty people. Each amount is the entire approved liability still available after prior allocations, including immutable credit adjustments. Any pending report/correction, changed roster, absent/currently revoked recipient, expired admission, cap violation, unresolved earlier item, or stale earlier-item evidence prevents review. Earlier provider items must have an exact current read within five minutes before a new payment can use the released or remaining balance. A liability below an already-paid or reserved amount remains visibly held for credit review; no automatic deduction or clawback is authorized.

An approval binds all original payable IDs/digests/deltas, recipient versions, currency, amounts, isolated merchant, exact actor/session and production/settlement/payout revisions. Its authority expires ten minutes after approval. The grant and durable job commit together. At dispatch, the worker locks the original instruction and rechecks the exact current session, expiry, production revision, settlement version, roster, admission and allocation. It then commits a unique immutable dispatch record before the first provider POST. A later revocation cannot promise to stop an already claimed transfer.

Schema 10 adds an encrypted append-only record ledger, verified revision cursor and immutable merchant/resource ownership bindings. Every read verifies the retained request and record hashes, metadata, sequence and canonical production marker. Producer commands also use the shared tenant-scoped command registry, preventing cross-endpoint identity reuse. Generic production events contain no recipient address, private hours or financial payload. Source application cannot replace a production after recipient or payout history exists.

## Unknown outcomes and current evidence

After a saved dispatch, worker continuation never calls create again. A retained batch identity leads only to the original batch and item GETs. A crash after dispatch but before a retained response, an unreadable response or an unidentified duplicate keeps the allocation reserved. **Locate original batch** accepts a separately reviewed candidate identity for a read only; it binds the resource only when the full sender identity, every item, each recipient and every amount match. A rejected candidate can be corrected through another explicit original-read review. No new batch is substituted.

Complete, bounded pagination is required. Partial collections, duplicate items, changed totals, foreign recipients, wrong parents, unexpected status values and ownership conflicts cannot qualify payment. The complete batch read queues distinct durable original-item reads. A newer incomplete batch or unverified item withdraws current proof while retaining historical success. Terminal regressions such as a previously credited item becoming `FAILED` remain held for investigation rather than freeing another payment. Verified `FAILED`, `RETURNED`, `REFUNDED` and `REVERSED` items can release their original allocation for a new explicit approval; unresolved items never do.

Only actual `paypal_https` direct item `SUCCESS` observations project an immutable crew payment receipt. Controlled wire fixtures are forced to `sample`/`local_fixture`, even though the underlying core's metadata type describes live sandbox responses. The financial summary distinguishes currently verified crew payment from historical credited receipts. Fee values remain separate from principal; an omitted or currently unverified fee is unknown, never assumed zero. This does not establish the complete production P&L.

Cancellation requires a fresh exact `UNCLAIMED` item, a separate review note/check and a new expiring current-session authority. The core GETs and validates the original item again before one cancel POST. Unknown cancellation outcomes continue by reading that same item only. A verified `RETURNED` state is a return of that original payout, not a new invented refund. Cancellation history and earlier credited receipts remain immutable.

## UI, routes and recovery

- `/api/payouts` is the current producer's read/strict command boundary. `/api/payouts/review` computes a server-bound review without authority or provider work.
- `/api/payouts/work` checks current producer access and runs only this tenant's payout job kinds. It cannot wake tickets, rental captures, refunds or another production. The shared authenticated scheduled worker also resumes durable jobs.
- `/api/crew/payouts` requires the exact personal bearer capability and returns only its person's items; producer cookies cannot substitute. Payout API responses are private/no-store and do not enter offline crew caches.
- Browser writes normalize the strict schema before calculating and retaining the full canonical digest. Recovery binds actor, production, command kind, request identity and entire reviewed envelope. File import checks the original receipt without POSTing. Lost responses preserve their original instruction; manual retries use that same identity. A retry of an approval can recover the saved grant but cannot re-dispatch its provider POST.

The UI supports named native buttons, explicit labeled fields/checks, original receipt details, modal focus return/Escape, responsive item cards, loading/error/held/recovery states and print output. **Continue saved payout work** resumes existing durable work; **Read original provider items** queues a fresh exact observation. Neither grants a new transfer. A controlled runtime labels every simulated result and does not claim actual money movement.

## Qualification boundary

`npm run test:payouts` guards actual providers before environment loading and runs meaningful domain, recovery and isolated-PostgreSQL tests against the pinned core's actual HTTP encoder/decoder with an owned fake fetch. Tests cover complete collections, wrong recipients, current versus historical evidence, unknown fees, credits, concurrent claims/replays, lost-response and crash holds, duplicate recovery, expired/revoked/changed authority, cancellation, cross-tenant ownership, private personal reads, strict HTTP boundaries and payout-only jobs. The first fake transport lacked the OAuth `token_type` field, failed closed as not sent, and was corrected; its original failed log remains retained privately.

Native browser and actual-provider qualification are separate root-owned gates. Provider credentials remain disabled in lead QA; a passing transport fixture is never a PayPal capability or ownership claim. Original financial history and all earlier frozen native/provider attempts are preserved. Invoices, scoped Toolkit qualification, baseline costs/full P&L, operational completion, tour/production/roster admission, swaps, broader evaluation, real-phone/practitioner evidence and film remain active full-plan work.
